## Unreleased

- `roles/site_agents` runtime directories: `~/.local/state` (`site_agents_state_dir`) is kept at mode `0700`, not `0755`. It holds agent reports and private session state, djbclark-ade tools (`ade-progress`, `ade-backup-stores`, `fable-wait`) create it `0700`, and every full apply used to widen it (found in the check-mode preview for #302; operator approved 2026-11-22). Subdirectories keep their own modes. (2026-11-22)
- `brew-fast-upgrade` (`roles/site_agents`): new `run_macroscope_pass` runs `MACROSCOPE_REQUIRE_CHECKSUM=1 ~/.local/bin/macroscope update --yes` (stdin `/dev/null`) once per invocation (attempt 1, not every retry), which runs Macroscope's installer script fetched from macroscope.com (not separately verified) to update the Macroscope local CLI and its agent plugin for the tools saved at install time; the binary is checked against GitHub's asset digest when one is reported, and a missing digest fails the pass. Skipped until the CLI is installed. It never runs a review (reviews bill per KB from a non-renewable US$100 budget). A failed update is logged and does not fail verification, like the kiri and chrome-use passes. No `--no-path`: `update` forwarding of it is unproven, and the saved install state already skips shell edits. Tests pin the argv, env, stdin and the `declare -f` list (the review of #302). It is also skipped when `~/.local/state/macroscope/install.json` is missing (without it the installer could edit a login rc file for PATH). (2026-11-22)

- `claude/local-marketplace` `local-lsp` 1.0.6 (the four LOWs of the adversary review of #292): (L1) the unguarded fallback line is now also appended, with a UTC time, to `~/.local/state/lsp-guard/unguarded.log`, because Claude Code writes LSP stderr only to its debug log (`claude --debug`), so the stderr line alone was invisible; `tail` that file to see whether the RAM relief is off. (L4) the 1.0.4 rollback bullet no longer names a version number; 1.0.5 and 1.0.6 carry the same rollback line; `claude/local-marketplace/README.md` documents the guard, its dependency on the djbclark-ade checkout and the off switch, and its install line now names `site-public-djbclark` (it named `site-private-djbclark`). Meant to sit behind a one-click ExtraBar `run_script` button. Tests: `tests/test_chrome_tabs_menu.py`. (2026-11-21)

- New `bin/chrome-bookmarks-extrabar-sync` (stdlib Python) and `bin/hourly-updates.d/chrome-bookmarks`: keeps one static ExtraBar folder widget "Chrome bookmarks" (the Default profile's Bookmarks bar; links are `deep_link` actions targeting Safari, braces in URLs percent-encoded) first in the active preset, through ExtraBar's `extrabar-mcp` helper. State (tree sha256, widget id, last approval request) in `~/.local/state/chrome-bookmarks-extrabar/state.json`; unchanged tree: silent no-op. - `bin/bgrun`, `bin/bgrun-container-guard`: follow-ups from the adversary reviews of PRs 287 and 288 (LOW findings). The container guard keeps the CLI in its own (the guard's) process group, so a group SIGKILL (`deadline run`, `gtimeout -k`) takes both down and a command that prompts on /dev/tty is never stopped (a group TERM reaches the CLI twice, under Apple's 3-signal threshold; stop a run with TERM to the bgrun pid); on a tty SIGINT is not forwarded and the guard's own handler does nothing, so a Ctrl-C during the final wait keeps exit 70; SIGUSR1/SIGUSR2 are forwarded again; `BG_CONTAINER_TEST_IDLE_READ`/`BG_CONTAINER_TEST_IDLE_WRITE` (test knobs, seconds from 0.1 to 600, else the default) set the give-up waits. `approve-local`: a single `revoke ID` is remembered in `tickets/.revoked`, so a copy of that ticket restored later is refused; `--scope` accepts only characters the approval dialog shows 1:1; the command text in the dialog has no quote, control or non-ASCII character; a refused file name is `%q`-quoted in `approvals.log`. Docs: autostart also restarts a deliberately stopped apiserver (`BG_CONTAINER_AUTOSTART=0` opts out). New tests cover each, with mutation checks.

- `bin/bgrun` and new `bin/bgrun-container-guard` (ADE queue 85 (a)-(c)): a `container ...` command now (a) starts a down Apple `container` apiserver once before it runs (`container system start --disable-kernel-install`; `BG_CONTAINER_AUTOSTART=0` turns it off; a status call slower than `BG_CONTAINER_STATUS_TIMEOUT`, default 20 s, is "unknown" and the command runs anyway; exit 72 if it stays definitely down), and (b) fails with exit 70 when the CLI exits 0 but reports an XPC "Connection invalid" error (any other status passes through; stdin, output and TERM/INT/HUP are relayed). Every command also gets `BGRUN_RUN_ID` and `BGRUN_RUN_START` so a gate can key its output directory by sha plus run instead of the sha alone.
- `bin/bgrun approve-local` tickets (operator 2026-11-21): `--for 7h` / `--until "tomorrow 8am"` [`--scope DIR`] [`-- CMD`] asks for ONE Touch ID and lets every `ci`-mode local run through until the expiry (shown as America/New_York 12-hour time in the dialog and the output); `status` (klist), `revoke [ID]` (kdestroy), `check [DIR]` (only a live any-command ticket counts), and `--ask` (a chooser: this run only / 1 h / 7 h / until a time). Tickets are 0600 files under `~/.local/state/bg/tickets/`, signed with a per-install salt (tamper-evidence, not a boundary), each use logged with time, directory and argv hash. The dialog starts with the expiry and scope (never cut; a command is cut at 120 characters with a marker; over 30 days is marked LONG-LIVED), a ticket needs the sudo-ask dialog, `revoke` rotates the salt, a ticket must be named for its own id and not be dated in the future. The one-shot form is unchanged.
